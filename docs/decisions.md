# 결정 기록

작업 중 애매했던 부분과 그때 내린 결정. 나중에 바꿔도 되는 것들이다.

## B — 영훈 담당 (scripts, access, negotiations, deals, ledger, worker)

### 범위
- 요청 문구는 "작가 쪽 흐름"이지만, 계약의 폴더 소유권상 scripts·access·negotiations·deals·ledger·worker 전부가 B 담당이고 A의 3단계 통합 시나리오(공개 → AI 요약 → 열람 → 채팅 → 제안 → 딜)가 이 API 전부를 필요로 하므로 계약 API 전체를 구현한다.

### 제안(Offer)
- 협상 하나에 PROPOSED 제안은 항상 최대 1개. 새 제안을 내면 기존 PROPOSED 제안은
  - 상대방이 낸 것이면 `COUNTERED`(역제안 처리),
  - 내가 낸 것이면 `WITHDRAWN`(새 제안으로 대체)으로 바꾼다.
- 수락·거절은 제안자가 아닌 참여자만, 철회는 제안자만 가능. 모두 PROPOSED 상태에서만.
- 비율은 0~100 정수, 합 100. 선급금은 0 이상 정수(원), 상한 20억. 기간은 1~120개월.

### 열람 권한
- 전문(fullText)은 계약대로 작가 본인과 열람 승인(APPROVED)된 제작자만. 관리자도 전문은 볼 수 없다(숨김 판단은 공개 정보로).
- 대본이 숨김(HIDDEN)이 되면 승인된 제작자도 전문을 볼 수 없다.

### 대본 (scripts)
- `GET /scripts`는 `{ items, nextCursor }` 형태의 커서 페이지네이션 (기본 20, 최대 50). 필터: `genre`, `q`(제목·로그라인), `mine=true`(내 대본 전체, 로그인 필요).
- `GET /scripts`, `GET /scripts/:id`는 비로그인도 접근 가능 (OptionalJwtAuthGuard). 로그인하면 응답의 `viewer`에 작가 여부·열람 요청 상태가 채워진다.
- 비공개(DRAFT·HIDDEN) 대본은 작가 본인과 관리자 외에는 404.
- 제작자가 전문을 받아갈 때마다 `ScriptAccessLog`를 남긴다 (작가 본인 조회는 기록하지 않음).
- `POST /scripts`는 WRITER 역할 필요. 수정·공개는 역할이 아니라 작가 본인인지로 판단.
- 공개는 `rightsDeclared=true`가 이미 저장되어 있거나 요청 본문에 `{rightsDeclared:true}`를 함께 보내면 된다. 이미 공개된 대본에 다시 호출하면 그대로 반환(멱등).
- 관리자가 숨긴(HIDDEN) 대본은 작가가 다시 공개할 수 없다(403). 수정은 가능.
- 공개 중인 대본의 권리 보유 진술은 철회할 수 없다(400).
- AI 요약 작업은 공개 시, 그리고 공개 상태에서 본문(fullText)이 바뀔 때 등록한다. Redis 장애로 등록이 실패해도 요청은 성공시키고 로그만 남긴다(3초 시간 제한). `AI_JOBS_DISABLED=true`면 등록하지 않는다(테스트용).

### 열람 요청 (access)
- PRODUCER 역할만 요청 가능, 자기 대본에는 불가.
- 같은 대본에 대한 재요청은 상태와 무관하게 409 (거절 후 재요청 불가). 필요하면 나중에 REJECTED → PENDING 재요청을 허용한다.
- `GET /access-requests?as=writer|producer&status=`: 생략하면 내 대본에 들어온 것과 내가 보낸 것을 모두 반환.

### 협상 (negotiations)
- 협상 시작은 열람 승인(APPROVED)을 받은 제작자만. 같은 대본·제작자 협상이 있으면 기존 것을 반환(멱등, 201).
- 메시지: `after` 없으면 최근 100개, 있으면 그 이후 최대 100개. 항상 오래된 순. 종료(CLOSED)된 협상에는 보낼 수 없고, 합의(AGREED) 후에는 계속 대화 가능.
- 협상 상세·메시지는 참여자와 관리자만, 그 외에는 404.

### 수락 = 매칭
- 수락하면 한 트랜잭션에서 Offer ACCEPTED, Negotiation AGREED, Deal(PENDING_CONTRACT), License(DRAFT, licensee=제작자, scope=조건 요약 문장) 생성.
- 독점(exclusive) 조건이 수락되면 같은 대본의 다른 OPEN 협상은 CLOSED, 그 협상의 PROPOSED 제안은 REJECTED.
- Deal을 ACTIVE로 바꾸는 API는 계약에 없어서 만들지 않았다 (계약서 서명 기능이 생기면 추가).
- `Deal.acceptedOfferId`는 계약에 관계(relation) 표기가 없어 id 값으로만 다루고, 응답에서는 별도 조회로 `acceptedOffer`를 채운다.

### 장부 (ledger)
- REVENUE·PAYOUT·FEE는 양수, ADJUSTMENT는 0이 아닌 정수(음수 가능). 상한 ±20억.
- 응답 `totals.balance = REVENUE - PAYOUT - FEE + ADJUSTMENT` (아직 지급되지 않은 금액의 근사치).
- 조회는 딜 참여자와 관리자, 기록은 관리자만.

### AI 요약 워커 (apps/worker)
- 워커는 API의 Prisma 클라이언트를 공유하지 않고 `pg`로 `"Script"` 테이블을 직접 읽고 쓴다. 계약상 @@map을 쓰지 않으므로 테이블·컬럼명이 모델·필드명과 같다는 점에 기대는 것이다.
- `aiSummary` JSON 형태: `{ summary, tags[], contentRating: 'ALL'|'12'|'15'|'19', model, generatedAt }`.
- `ANTHROPIC_API_KEY`가 있으면 Claude(`claude-opus-5-5`, 구조화 JSON 출력, 거절 시 서버측 대체 모델)로, 없으면 결정적 mock 요약기로 동작. `AI_SUMMARIZER=mock|claude`로 강제 가능.
- 정책 거절(refusal)은 재시도하지 않고 실패 처리, 그 외 오류는 BullMQ가 3회까지 지수 백오프로 재시도.

### 진행 상황
- A의 foundation이 4시간 동안 origin에 없어서 계약 ERD 기반 임시 환경(작업 폴더 밖 scratchpad)에서 검증했다. 실제 연결은 b-done.md "연결 시 할 일" 참고.
- 파트너 프롬프트와 파일 충돌을 피하려고 내 아침 보고는 `docs/morning-report.md`가 아니라 `docs/morning-report-b.md`에 썼다.

## A 파트도 영훈이 구현 (feat/b-fullstack)

파트너의 1단계가 올라오지 않아 A 파트(기반·인증·관리자·웹)까지 직접 구현하고 실제로 띄워 검증했다.

### 디렉터리 이름 — 파트너 작업과 겹치지 않게
파트너가 나중에 자기 작업을 올려도 같은 경로를 덮어쓰지 않도록 계약상 A 소유 이름은 쓰지 않았다.

| 계약상 A 경로 | 이 브랜치에서 쓴 경로 |
|---|---|
| `apps/web` | `apps/studio` (기존 `apps/web` MVP 뼈대는 그대로 두고 워크스페이스에서만 제외) |
| `apps/api/src/common` | `apps/api/src/core` (auth), 기존 `apps/api/src/prisma` 유지 |
| `modules/{auth,users}` | `modules/identity` |
| `modules/admin` | `modules/backoffice` (경로는 계약대로 `/admin/*`) |
| `docker/`, 루트 `docker-compose.yml` | `ops/dev.Dockerfile`, `ops/compose.yaml` (루트 compose는 손대지 않음) |
| `packages/shared` | 만들지 않음 (웹은 openapi-typescript로 생성한 타입을 직접 씀) |
| 루트 `CLAUDE.md` | 만들지 않음 (파트너가 만들 파일이라 충돌 방지). 내용은 README와 이 문서에 |

공용일 수밖에 없는 파일은 고쳤다: 루트 `package.json`·`pnpm-workspace.yaml`·`pnpm-lock.yaml`, `apps/api/prisma/schema.prisma`·`package.json`·`src/app.module.ts`·`src/main.ts`, `.github/workflows/ci.yml`, `README.md`.

### 결정
- pnpm 12 워크스페이스 (`packageManager: pnpm@12.11.2`, corepack). pnpm 12는 승인 안 된 빌드 스크립트가 있으면 설치를 실패시키므로 `pnpm-workspace.yaml`의 `allowBuilds`에 prisma·@prisma/engines·@swc/core·esbuild를 허용, 텔레메트리(@scarf/scarf)·선택적 네이티브 가속(msgpackr-extract)은 거부.
- 루트 스크립트 이름은 `stack`(`pnpm up`은 pnpm 기본 명령이라 못 씀).
- 스키마: 계약 ERD 그대로. 이전 MVP 초안(User/Script/Proposal)에서 바꾸는 마이그레이션 `b_contract_schema`. 데이터 손실 경고 때문에 `migrate dev`가 비대화형 환경에서 멈춰서 `migrate diff`로 SQL을 만들었다. 기존 개발 DB에 데이터가 있으면 적용이 실패할 수 있다 → `down -v`로 초기화.
- 인증: argon2id(`@node-rs/argon2`, 네이티브 빌드 스크립트 불필요), JWT 7일. 토큰은 응답 본문과 httpOnly 쿠키(`vmp_token`, SameSite=Lax) 둘 다로 주고, 가드는 Bearer 헤더와 쿠키를 모두 받는다. 매 요청마다 사용자를 DB에서 다시 읽어 역할 변경이 바로 반영된다.
- 가입으로는 ADMIN 역할을 얻을 수 없다(시드 관리자만). 없는 이메일 로그인도 같은 비용의 해시 검증을 해서 응답 시간으로 가입 여부를 알 수 없게 했다.
- 계약 외 추가 API: `POST /auth/logout`(쿠키 삭제), `GET /admin/scripts`(숨김 포함 목록), `PATCH /admin/scripts/:id/hide`에 `{hidden:false}`로 숨김 해제.
- 웹은 `/api/*`를 Next.js rewrite로 API에 넘긴다. 같은 출처라 httpOnly 쿠키를 CORS 없이 쓸 수 있다.
- 실제 API가 있으므로 MSW 목은 만들지 않았다.
- Next.js의 Cache Components는 켜지 않았다. 화면은 대부분 클라이언트 컴포넌트에서 데이터를 불러온다.
- 분배 비율은 슬라이더와 숫자 입력을 함께 둔다(정밀 입력, 테스트 안정성).
- OpenAPI 생성은 데코레이터 메타데이터가 필요해서 tsx가 아니라 tsc로 컴파일해 실행한다 (`pnpm --filter api openapi`).
- 시드 대본 id는 `seed_script_*`로 고정해서 시드를 여러 번 돌려도 중복되지 않게 했다.
- Playwright는 Pixel 7(모바일 폭) 한 프로젝트로 돌린다. 컨테이너에서 `http://studio:3000`으로 접속하므로 `allowedDevOrigins: ['studio']`가 필요하다.

## 역할 구조: 일반 계정 + 관리자 승인

- 가입하면 역할이 없는 **일반 계정**(`roles = []`)이 된다. 별도 USER 역할 값을 만들지 않고 빈 배열을 일반으로 본다 (계약의 Role 열거형을 그대로 유지).
- 대본 제공자(WRITER)·영상 제작자(PRODUCER)는 `RoleRequest`로 신청하고 관리자가 승인하면 `User.roles`에 추가된다. ADMIN은 신청 대상이 아니다.
- 가입 API의 `roles`를 `requestedRoles`(선택)로 바꿨다. 넣은 권한은 가입과 함께 신청(PENDING)된다. **계약의 `POST /auth/signup` 요청 형태가 바뀐 것**이므로 파트너와 맞춰야 한다.
- 같은 권한에 대기 중인 신청이 있으면 409, 이미 가진 권한이면 400. 거절된 뒤에는 다시 신청할 수 있다.
- 승인은 신청 상태 변경과 역할 추가를 한 트랜잭션으로 처리한다. 인증 가드가 매 요청마다 사용자를 다시 읽으므로 승인 즉시 반영된다 (다시 로그인할 필요 없음).
- 새 API: `POST /role-requests`, `GET /role-requests/mine`, `GET /admin/role-requests?status=`, `POST /admin/role-requests/:id/approve`, `/reject`.
- 사용자용은 `modules/membership`(파트너의 `users`와 겹치지 않는 이름), 관리자용은 `modules/backoffice`에 두었다. `User` 모델에 RoleRequest 관계 필드 2개를 추가했다 (계약상 A 모델 수정).
- 마이그레이션 `b_role_request`.
- 화면에서 역할 이름은 "대본 제공자", "영상 제작자", "관리자", 역할이 없으면 "일반"으로 표시한다.
- 시드 계정은 역할마다 아이디와 비밀번호를 다르게 했다 (`@vmp.dev`). 이전 `@example.com` 시드 계정은 없어졌으므로 기존 개발 DB는 `down -v`로 초기화하는 것이 깔끔하다.

## 대본 업로드, 검토 후 메시지, 관리자 로그

- 업로드: `.txt` `.md` `.fountain` `.docx` `.pdf`, 최대 5MB. 원본 파일은 저장하지 않고 추출한 본문만 `Script.fullText`에 넣는다(저장소 운영 부담·개인정보 최소화). 업로드 사실은 `ScriptUpload`에 남긴다 (파일명, 형식, 크기, 글자 수).
- 텍스트 파일은 UTF-8을 먼저 시도하고 실패하면 EUC-KR로 읽는다. 한글 `.hwp`는 지원하지 않는다 (`.docx`/`.pdf`로 저장해 올리도록 안내). 스캔 이미지 PDF(글자 없는 PDF)는 거부한다.
- 파일로 만든 초안은 제목=파일 이름, 장르="미정", 로그라인·시놉시스는 빈 값. 그래서 **공개할 때 로그라인·시놉시스·장르·전문이 채워져 있는지 검사**를 추가했다.
- 제작자 메시지(`POST /scripts/:id/contact`)는 "검토 후"를 열람 승인 + 실제로 전문을 연 기록(ScriptAccessLog)으로 판단한다. 메시지는 별도 테이블이 아니라 그 대본·제작자의 협상 대화(Message)에 이어서 남긴다. 협상이 없으면 만든다.
- 전문 열람 기록은 같은 사람이 같은 대본을 10분 안에 다시 연 경우 한 번으로 본다 (상세 화면이 AI 요약을 기다리며 3초마다 다시 불러와서 기록이 부풀던 문제).
- 관리자 활동 로그: `GET /admin/logs/messages`, `/views`, `/uploads` (검색 q, 커서 페이지). 메시지 로그는 받는 사람(협상의 다른 참여자)도 함께 보여준다. 제작자 메시지 패널에 "관리자가 기록을 볼 수 있다"고 안내한다.

## 계정별 개발 주소

- 로그인 쿠키는 포트가 아니라 호스트 이름으로 나뉘어서, 포트를 계정마다 다르게 주면 로그인이 섞인다. 그래서 계정마다 하위 주소(`<계정>.localhost:3000`)를 배정했다.
- `/dev/accounts`(목록)와 `/dev/login?as=<계정>`(자동 로그인)은 `NEXT_PUBLIC_DEV_ACCOUNTS=true`일 때만 동작한다. 시드 비밀번호가 화면 코드에 들어가므로 운영 빌드에서는 이 값을 켜지 않는다.
- Next.js 개발 서버가 다른 호스트의 개발 리소스 요청을 막지 않도록 `allowedDevOrigins`에 `*.localhost`를 추가했다.

## AI 요약 새로고침, 최근 수정 시각, 미리보기 대본

- `Script.contentUpdatedAt`: 내용(제목·로그라인·시놉시스·장르·전문·미리보기)이 바뀐 시각. 공개·숨김 같은 상태 변경과 AI 요약 저장은 포함하지 않는다 (`updatedAt`은 이런 것까지 바뀌어서 "최근 수정"으로 쓰기 어렵다).
- 요약 대상 필드(제목·로그라인·시놉시스·장르·전문)가 바뀌면 상태와 관계없이(초안 포함) 요약을 다시 요청한다. 미리보기만 바뀌면 요약은 그대로 둔다 (요약은 전문 기준).
- `Script.aiSummaryRequestedAt`이 `aiSummary.generatedAt`보다 나중이면 "만드는 중"(`aiSummaryPending`). 요청 시각을 큐 등록 **전에** 기록하고(빠른 워커가 먼저 끝나도 안전), 큐 등록에 실패하면 되돌린다(영원히 "만드는 중"으로 남지 않게).
- 작성자 수동 새로고침 `POST /scripts/:id/summary/refresh`: 같은 요청이 30초 안에 아직 진행 중이면 429, 큐를 쓸 수 없으면 503.
- 공개 시에는 요약이 없을 때만 요청한다 (내용이 바뀔 때마다 이미 만들어 두므로).
- 여러 번 연달아 고치면 작업이 여러 개 쌓일 수 있지만, 워커는 처리 시점의 최신 본문을 읽으므로 마지막 요약은 최신 내용을 반영한다.
- 미리보기 대본(`Script.previewText`, 최대 5만 자): 작가 본인과, **공개 대본을 보는 PRODUCER**에게만 내려준다. 열람 승인은 필요 없다. 일반 계정·비로그인·관리자에게는 null. 빈 값으로 저장하면 미리보기 없음.
- 미리보기 파일 업로드 `POST /scripts/:id/preview/upload`. 업로드 로그(`ScriptUpload.kind`)에 FULL/PREVIEW를 구분해 남긴다.
- 편집 화면은 폼 상태(처음 불러온 값)와 최신 서버 상태(요약 진행·수정 시각)를 분리했다. 요약을 기다리며 3초마다 다시 불러와도 입력 중인 내용이 지워지지 않는다.
- 개발 서버(`nest start --watch`)가 수정 도중의 중간 상태를 컴파일하다 실패한 뒤 예전 코드로 계속 도는 경우가 있었다. 스키마·DTO를 크게 바꾼 뒤에는 `docker compose -f ops/compose.yaml restart api`.

## 계정 구조 변경: 일반·관리자, 프로필 공개, 코인, 정지·탈퇴

요청: 계정은 일반과 관리자 두 가지, 관리자 승인 없이 일반 계정이 대본 제공·영상 제작을 하되 프로필과 이메일을 반드시 공개, 메시지·미리보기·업로드에 코인, 코인 구매, 관리자 정지, 탈퇴 후 재가입 허용·정지 이메일 재가입 금지.

- 이전의 권한 신청(`RoleRequest`)과 대본 제공자·영상 제작자 역할 구분을 없앴다. `Role` 열거형은 계약 호환을 위해 남겼고 실제로는 `ADMIN`만 쓴다. 마이그레이션 `b_accounts_coins`가 기존 사용자의 WRITER·PRODUCER 값을 지운다.
- "프로필과 이메일 공개" = 소개(bio) 작성 + `profilePublic` + `emailPublic`. 셋 다 충족해야 `creatorReady`. 소개 없이 프로필 공개는 400. `CreatorGuard`가 창작 행동(대본 작성·수정·업로드·공개·요약 새로고침, 열람 요청·승인·거절, 협상·메시지·제안·수락, 미리보기 열람)을 막고 `PROFILE_NOT_PUBLIC`을 돌려준다. 관리자는 창작 활동 대상이 아니다.
- 대본의 작가와 상대방(협상의 writer/producer)은 이제 역할이 아니라 "그 대본을 쓴 사람 / 열람·협상하는 사람"으로 정해진다.
- 코인 가격(임의로 정함, `apps/api/src/modules/wallet/coin-pricing.ts`): 메시지 1, 미리보기 열람 3(대본당 한 번, 열람권 `ScriptPreviewUnlock`), 대본 파일 업로드 5(새 초안·전문 교체·미리보기 모두). 직접 작성·공개·열람 요청·제안은 무료. 가입 보너스 10코인. 패키지 10코인 1,000원 / 55코인 5,000원 / 120코인 10,000원.
- **실제 결제는 연동하지 않았다.** 구매는 테스트 결제로 바로 충전하고 화면에 그렇게 표시한다. 실제 PG를 붙일 때 `WalletService.purchase`를 결제 확인 웹훅 뒤로 옮겨야 한다.
- 코인 차감은 "잔액 ≥ 비용일 때만 감소"하는 조건부 update로 동시성에서도 음수가 되지 않는다. 차감과 대상 작업(메시지 생성, 업로드 반영, 열람권 생성)은 한 트랜잭션이라 코인이 부족하면 작업도 일어나지 않는다(402 `INSUFFICIENT_COINS`). 업로드는 본문 추출에 성공한 뒤에만 차감한다. 모든 증감은 `CoinTransaction` 원장에 거래 후 잔액과 함께 남는다.
- 정지(`status = SUSPENDED`): 관리자만, 일반 계정만(관리자·자기 자신·탈퇴 계정 불가). 인증 가드가 매 요청마다 상태를 확인해 즉시 차단(403 `ACCOUNT_SUSPENDED`), 로그인 시 사유 표시. 정지된 작가의 대본은 공개 목록·상세에서 빠진다(관리자만 볼 수 있음, 데이터는 그대로). 정지된 계정의 이메일로 가입하면 403 `SUSPENDED_EMAIL`.
- 탈퇴(`DELETE /me`, 비밀번호 확인): 기록(메시지·딜·장부)은 남기고 개인정보를 지운다. 이메일을 `withdrawn+<id>@deleted.invalid`로 바꿔 원래 이메일을 비워 두므로 같은 이메일로 새 계정을 만들 수 있다. 공개 대본은 DRAFT로 내리고, 진행 중인 협상은 CLOSED, 대기 중인 열람 요청은 REJECTED, 남은 코인은 소멸.
- 관리자 코인 지급·회수(`POST /admin/users/:id/coins`), 코인 로그(`GET /admin/logs/coins`). 관리자 사용자 목록에 상태·코인·공개 여부, 상태 필터와 검색.
- 상단 메뉴가 늘어 좁은 화면에서 글자가 세로로 쌓이던 문제를 고쳤다(메뉴 글자는 줄바꿈 금지, 공간이 모자라면 메뉴 줄이 다음 줄로).

## 출연자 등록·캐스팅 (Varev 쪽 Claude, feat/b-talent-casting)

기준 문서: [`docs/policies/likeness-policy.md`](policies/likeness-policy.md). 규칙은 `apps/api/src/modules/talent/likeness-policy.ts` 한 곳에 모았다.

### 계정 구조에 맞춘 것
- 새 역할을 만들지 않았다. **일반 계정이 출연자 프로필(`TalentProfile`)을 만들면 출연자**, 본인인증한 성인 일반 계정이 **보호자**가 된다. 관리자 계정은 출연자가 될 수 없다.
- 출연자 등록에는 프로필·이메일 공개(`CreatorGuard`)를 요구하지 않는다. 출연자는 활동명만 공개되고 실명·이메일은 캐스팅 목록에 나오지 않는다.
- 기획사는 **딜의 작가와 제작자**다. 딜 하나에 작품(`Project`) 하나. 배역이 정해지면 같은 배역의 다른 협상은 자동 종료.
- 계정이 탈퇴(`WITHDRAWN`)하면 1시간마다 도는 정리 작업이 출연자 등록을 철회 처리한다. 정지(`SUSPENDED`)는 일시적일 수 있어 철회하지 않고, 정지 중에는 캐스팅만 막힌다.
- 코인은 쓰지 않는다 (출연 협상은 무료).

### 철회·삭제 (정책 3·5·6장)
- 철회는 앞으로만 효력: 새 제안 즉시 차단, 원본·모델은 7일 숙려 후, 진행 중 계약이 있으면 제작 기한(최대 90일) 뒤 삭제. 공개된 작품은 계약 기간 동안 유지.
- 계약 위반 사유 5개는 신고 즉시 비공개, 관리자 7일 안 판단. 단순 변심(`PERSONAL_WITHDRAWAL`)·인격권 침해(`PERSONALITY_HARM`)는 공개 유지 후 합의·심사.
- 조기 종료 보상 기본값: 받은 고정 출연료 반환 + 50%. **변호사 검토 전 임시값.**

### 데이터 보호
- 원본은 파일마다 다른 키(AES-256-GCM)로 암호화하고 키는 마스터 키로 감싸 DB에 둔다. 삭제할 때 감싼 키도 지워 백업까지 복구 불가.
- 개발은 `apps/api/.likeness-store/`(gitignore) 로컬 디스크와 고정 개발 키. 운영은 `LIKENESS_MASTER_KEY`가 없으면 시작하지 않는다. 오브젝트 스토리지 + KMS로 옮겨야 한다.
- 본인인증·셀카 확인은 **가짜 provider**만 있다 (`test:<실명>:<YYYY-MM-DD>` 토큰, 셀카 파일에 `MISMATCH`/`NOT-LIVE`가 있으면 실패). `NODE_ENV=production`에서는 `ALLOW_FAKE_VERIFICATION=true` 없이 시작하지 않는다.
- 생년월일은 저장하지 않는다. 미성년자는 만 19세가 되는 날만 저장한다.

### 테스트
- 통합 테스트는 공유 DB에서 고유 접미사로 만들고 지운다. 정리 작업(`runMaintenance`)은 테스트에서 출연자 id로 범위를 한정해 다른 데이터를 건드리지 않는다.

## 흥행 판단 모델 (Varev 쪽 Claude, feat/b-hit-model-foundation)
기준 문서: [`docs/hit-model.md`](hit-model.md)
- **LLM API로 점수를 매기지 않는다.** 처음에는 AI 요약에 PD 관점 커버리지 점수를 넣었다가 되돌렸다. 누구나 같은 API로 만들 수 있어 자산이 안 되고,
  실사 촬영을 전제한 의견이 섞였고, 실제 성과와 연결되지 않기 때문이다. 대신 대본 벡터 + 우리 작품 성과로 학습하는 자체 통계 모델을 만든다.
- 모델은 별도 **Python 서비스**(`services/ml`, FastAPI)로 둔다. 수치 계산 생태계(numpy, 임베딩 모델)가 파이썬에 있고, API·워커와는 HTTP로만 이야기한다.
  내부 토큰(`ML_TOKEN`)을 쓰고 포트를 열지 않는다.
- 테이블은 Prisma가 만들고(`ScriptEmbedding`, `HitModelVersion`), ML 서비스는 SQL로 읽고 쓴다(마이그레이션하지 않음). 워커와 같은 방식이다.
- 벡터는 pgvector 대신 `Float[]`로 저장한다. 수백~수천 편 규모에서는 메모리에서 계산해도 충분하고, DB 이미지·확장 설치를 바꾸지 않아도 된다. 수만 편이 되면 pgvector로 옮긴다.
- 기본 임베더는 문자 n그램 해시(외부 API·모델 다운로드 없음, 결정적). 공개 임베딩 모델(bge-m3)은 선택으로 우리 서버에서 돌린다.
- 정답은 채널 크기를 보정한 도달 + 반응(좋아요, 긍정 댓글 ×3)의 상위 20%. 공개 후 7일 이상, 30일에 가장 가까운 기록.
- 모델은 시간 순서 검증에서 장르 평균 이상일 때만 활성화한다. 정답 있는 대본이 100편(`ML_MIN_TRAINING_PAIRS`) 전에는 비슷한 작품만 보여 준다.
- **작가 본인에게는 판단 결과를 보여 주지 않는다**(403). 점수에 맞춰 쓰는 것을 막기 위해서다.
- 대본별 **학습 동의**(`trainingConsent`)는 선택, 기본 동의 안 함. 학습 데이터에는 동의한 대본만 들어간다. 공개 대본은 동의와 상관없이 판단·추천 대상이며, 동의 화면에 적었다.
- 워커는 요약 작업 때 벡터화도 요청한다. 벡터화 실패는 요약 작업을 실패시키지 않는다.
- 합성 데모 데이터(`db:seed:ml-demo`)는 기본 시드에 넣지 않는다. 화면 흐름 확인용이고, 데모 작가 계정 하나에 묶어 한 번에 지운다.
- CI에 Python 린트·테스트 단계를 같은 `ci` 작업 안에 더했다(필수 검사 이름 유지). `.github/` 변경이라 영훈 님 승인이 필요하다.

## 흥행 판단 가능성 검증 (Varev 쪽 Claude, feat/b-feasibility-study)
기준 문서: [`docs/feasibility-study.md`](feasibility-study.md), 약정 항목 초안: [`docs/policies/creator-pilot-agreement-draft.md`](policies/creator-pilot-agreement-draft.md)
- 데이터 확보 방식을 정하기 전에 **"대본만 보고 같은 채널 안에서 잘될 영상을 가려낼 수 있는가"**부터 확인한다.
- **크롤링하지 않는다.** "교육·연구용"으로 정해도 유튜브 정책(스크래핑 금지)과 저작권 문제가 그대로이고, 자막은 촬영 전 대본이 아니라서 질문에도 맞지 않는다.
- 처음 제안한 "일반 API 키로 공개 통계 조사"도 뺐다. 개발자 정책이 콘텐츠 소유자가 다른 채널의 데이터를 합치는 것(III.E.2.a), API 데이터로 새 지표를 만드는 것(III.E.4.h),
  통계를 30일 넘게 보관하는 것을 막는다. 정책 본문을 2026-10-13에 확인했다.
- 대신 **크리에이터 제휴 파일럿**: 크리에이터가 자기 대본과 자기 스튜디오에서 내려받은 표 데이터를 약정에 따라 직접 준다. 우리는 API를 부르지 않는다.
- 정답은 **채널 안 비교**(채널 중앙값 대비 도달·평균 조회율·반응)다. 채널마다 구독자·노출이 크게 달라서다. 파일럿 데이터에는 공개 시점 구독자 수가 없다는 점도 있다.
- 평가는 "채널 빼고 맞히기"와 "시간 순서" 두 가지. AUC는 같은 채널 안의 쌍만 센다. 처음에는 묶음별 점수를 한 줄로 세웠는데,
  신호가 없는 합성 데이터에서 0.39가 나왔다(묶음마다 절편이 달라서 생기는 착시). 그래서 바꿨다.
- 판정 기준(GO / MORE_DATA / NO_GO)을 데이터를 보기 전에 코드와 문서에 고정했다. GO에는 구간 아래쪽 > 0.5, 순열 p ≤ 0.05, AUC ≥ 0.60, 리프트 ≥ 1.5, 시간 순서 AUC > 0.5가 모두 필요하다.
  부트스트랩 구간이 실제보다 좁게 나와서(합성 데이터 순열 분포와 비교해 약 1.5배 차이), 순열 검정을 함께 보도록 했고 표본 크기 계산에도 1.5배를 반영했다.
- 목표 표본은 대본 1,000편(채널 25~30곳). AUC 0.60을 82% 확률로 잡을 수 있다. 300편·8곳부터 첫 분석.
- 블라인드 테스트는 GO일 때만 한다. 문제지를 만드는 순간 모델 점수를 정답지에 적어 두어, 결과를 보고 고칠 수 없게 했다.
- 파일럿 데이터는 `services/ml/research/data/`에 두고 저장소·도커 이미지에서 뺐다. 제품 DB와 섞지 않는다. 철회 시 7일 안에 지운다.
- 분석 도구는 `services/ml/research/`에 두고 `hitmodel`의 계산 함수(장면 나누기, 임베더, 로지스틱 회귀)를 그대로 쓴다. 검증한 방법이 제품 모델과 같아야 결과를 옮겨 쓸 수 있다.
- 신호 없는 합성 데이터 25개 중 1개(4%)가 GO로 나왔다. 최소 표본(300편)에서는 AUC가 우연히 0.6을 넘는 일이 드물지 않아서, 1,000편 전의 GO는 "잠정 GO"로 두고 1,000편에서 다시 확인한다.

## 흥행 판단 요소 후보와 대리 검증 (Varev 쪽 Claude, feat/b-story-features)
기준 문서: [`docs/hit-features.md`](hit-features.md)
- 대본을 사기 전에 무엇을 잴지부터 정한다(Varev 제안). 후보 18개를 도입·긴장/감정 흐름·반전·인물/대사·속도로 나눴다.
- 요소는 LLM 없이 사전·규칙으로 잰다(`story-lex-v0`). 같은 글이면 같은 값이 나오고, 사전을 고치면 버전을 올린다.
- **해적판 PDF는 쓰지 않는다.** 시험용이어도 복제권 침해이고, 출처 불명 파일은 악성코드 위험이 있으며, 그 결과로 정한 요소가 제품에 들어간다. 산 책 스캔도 하지 않는다(데이터 분석 예외 없음).
- 대신 프로젝트 구텐베르크 공공 저작물 + 위키데이터(CC0) 영상화 기록으로 "같은 작가 안에서 영상화된 작품 vs 아닌 작품"을 비교한다.
  저자 사망 1962년까지(한국에서도 보호 기간 종료), 영어 원작만(번역자 권리를 피하려고). IMDb는 비상업 약관이라 쓰지 않는다.
- 한국 공공 저작물은 위키데이터에 영상화 기록이 6편뿐이라 대리 검증에 못 쓴다. 한국어 측정 확인에만 쓴다.
- 구텐베르크는 사이트 자동 수집을 막으므로 공식 미러(mirrors.xmission.com, 처음 쓴 aleph.pglaf.org는 25KB/s로 너무 느렸다)에서 2초 간격으로 받는다. 본문은 `research/data/proxy/`에 두고 저장소에 넣지 않는다.
- 대리 검증 결과로 요소를 버리지 않는다. 소설 → 영화의 이야기 매력과 단편 영상 성과는 다르고, "첫 3초" 같은 요소는 소설로 잴 수 없다. 우선순위만 정한다.
- 요소별 검정은 홀름 보정. 순열 2,000회(요소 19개면 380회 이상이어야 보정을 넘을 수 있다).
- 대리 검증 1차: 긴장 표현이 유일하게 보정 후 신호였지만, 장르를 떼자 장르 기록 유무(유명한 장르물 여부)의 차이로 대부분 설명됐다. 그래서 긴장은 "장르 신호"로 내리고,
  장르를 떼도 유지된 인물 집중도(인물 수가 적고 주인공 비중이 큼)를 1순위 후보로 올렸다. 장르 기록이 58%뿐이고 유명 작품에 치우쳐 있어 결론은 잠정이다.
- 우리 모델의 가치는 장르 안에서 더 맞히는 것이어야 한다(장르는 PD가 이미 안다). 파일럿의 채널 안 비교가 이 조건을 따른다.
- 장르 자료를 구텐베르크 공개 카탈로그(사서 주제·서가)로 바꿨다(80% 작품에 장르, 위키데이터는 58%). "Movie Books"(영상화된 책) 서가와 베스트셀러·명작 목록은 정답·유명세가 새므로 뺐다.
  결과: 긴장 표현은 장르·길이를 회귀로 떼도 유의(0.614)해서 "대부분 장르"라는 위키데이터 때 결론을 "일부 장르"로 고쳤다. 인물 집중도는 그대로 유지,
  벡터 모델은 같은 작가·같은 장르 안에서도 0.619로 유의했다.
- 벡터·낱말 탐색은 "찾은 데이터로 바로 검정하지 않는다"를 지켰다. 흐름 요소는 정의를 먼저 정했고(결과: 신호 없음), 특징 낱말은 작가를 반으로 나눠 찾고 확인했다(양쪽 다 0.64).
  찾은 낱말은 "보여 주기(동작·사물·구어) vs 말하기(추상·논평)" 축으로 읽혀서, 이를 "보여 주기 지수" 후보로 올렸다. 한국어 사전은 파일럿 대본에서 같은 방식으로 새로 만든다.
- bge-m3로 다시 보니 벡터 흐름 요소는 여전히 신호가 없었고, 의미 벡터 모델은 같은 작가·같은 장르 안에서 0.636(p 0.010)으로 n그램(0.619)보다 나았다.
  모델 캐시는 저장소 안(`services/ml/research/data/hf-cache`, 저장소에서 제외)에 두었다. 같은 가중치가 두 형식으로 받아져 4.3GB를 쓴다.
- 2단계-2(Varev 제안): 영상화된 작품끼리 흥행을 가르는 대리 검증을 더했다. 흥행 점수 = 재영상화 + 연대·형식을 뺀 인지도(위키백과 언어판) + 지금의 관심(조회수), 상위 1/3.
  박스오피스·평점은 기록이 드물고 IMDb는 비상업 약관이라 뺐다. 결과: 보정 후 남은 요소 없음. PD가 고르는 요소(인물 집중도·보여 주기)는 흥행을 가르지 못했고,
  1단계에서 차이가 없던 감정 전환 횟수가 흥행에서만 후보(0.692, 보정 0.095)로 보였다. 벡터 모델은 작가 33명으로는 흥행에 옮겨 가지 않았다(0.353).
  그래서 흥행 예측의 본 검증은 크리에이터 파일럿으로 남긴다.
- 대리 검증을 TV 에피소드(위키백과, 78개 시리즈 9,967화)와 영화 줄거리(CMU Movie Summary Corpus, 6,930편)로 넓혔다. 둘 다 CC BY-SA라 출처 표시로 상업적 이용이 가능하다.
  나무위키 시청률(비상업), IMDb(비상업), 대본 사이트(저작권)는 쓰지 않았다.
  TV는 같은 시리즈 안에서 줄거리로 거의 못 맞혔고(0.498), 영화는 같은 장르·시기 안에서 0.568이었다(예산 효과가 섞일 수 있음).
  종합: 이름 붙인 요소는 자료마다 방향이 엇갈렸고, 의미 벡터 모델이 더 일관되게 쓸모 있었다. 흥행 예측 신호는 작으므로 파일럿 GO 기준(0.60)을 낮추지 않고 그대로 둔다.
