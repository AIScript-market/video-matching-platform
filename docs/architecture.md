# 아키텍처 및 개발 환경 계획

모노레포 하나에 API 서버 하나를 두고, 서버 안을 도메인 모듈로 나눈 **모듈형 모놀리스**로 시작한다. AI 처리만 별도 워커로 분리한다. 로컬 환경은 Docker Compose로 통일하고, 협업은 GitHub PR과 CI로 한다.

초기 팀에게 마이크로서비스는 관리 부담만 크다. 코드 안에서 도메인 경계를 분명히 나누고 모듈마다 담당자를 정하면 여럿이 동시에 개발해도 충돌이 적다.

## 현재 단계

- **팀**: 2명
- **범위**: 대본 작가 ↔ 영상 제작자 중개만 먼저 만든다 (회원, 대본 등록, 제작 제안, 매칭).
- **언어**: TypeScript 하나로 웹(Next.js)과 API(NestJS)를 모두 만든다. 2명이 프론트와 백엔드를 오가며 일할 수 있고 타입을 공유할 수 있다. Python AI 워커, Redis, 파일 저장소(S3)는 해당 기능을 만들 때 추가한다.
- **DB 스키마**: `apps/api/prisma/schema.prisma`의 `User`, `Script`, `Proposal`

아래는 최종 목표 구조다.

---

## 1. 전체 구조

```
[Next.js 웹] ──► [API 서버 (모듈형 모놀리스)] ──► PostgreSQL
[관리자 콘솔] ─┘         │                    ├─► S3 (대본·미디어 / 초상·음성은 별도 암호화 버킷)
                         └─► 작업 큐(Redis) ──► [AI 워커 (Python, GPU)]
                                                  요약 · 음성 합성 · 얼굴 합성
[PG사] ◄──► 결제 · 지급대행 · 웹훅
```

| 모듈 | 하는 일 |
|---|---|
| `auth/user` | 역할 관리(작가·제작자·배우·성우·관리자), 본인인증 |
| `script` | 대본 업로드와 버전 관리, AI 요약 요청 |
| `talent` | 배우·성우 프로필, 얼굴·음성 자산 등록 |
| `license` | 동의·라이선스 기록, 사용 범위 검증 |
| `project` | 매칭, 계약, 단계별 진행(마일스톤) |
| `settlement` | 결제, 수익 분배, 장부(원장), 지급 |

AI 작업은 요약이 수십 초, 합성은 몇 분까지 걸린다. HTTP 요청 안에서 바로 처리하지 말고, 큐에 넣어 비동기로 돌린 뒤 진행 상태를 알려주는 방식으로 만든다.

## 2. 기술 스택

| 영역 | 선택 | 이유 |
|---|---|---|
| 웹 | Next.js + TypeScript | |
| API | NestJS (TypeScript) | 프론트와 타입 공유. 팀이 Java에 익숙하면 Spring Boot도 가능 |
| AI 워커 | Python (FastAPI + Celery) | AI 라이브러리 생태계 |
| DB | PostgreSQL | 정산 데이터의 정합성 |
| 큐 | Redis | |
| 스토리지 | S3 호환 (로컬은 MinIO) | |
| 클라우드 | AWS 서울 리전 또는 NCP | 개인정보 국내 보관 |
| AI 모델 | 요약은 LLM API, 합성은 외부 API를 어댑터 뒤에 연결 | 나중에 자체 모델로 교체 가능 |

## 3. 협업 환경

### 최종 저장소 구조 (npm workspaces 모노레포)

현재는 `apps/web`, `apps/api`만 있다. 나머지는 필요해질 때 추가한다.

```
video-matching-platform/
├─ apps/
│  ├─ web/              # Next.js
│  ├─ admin/            # 관리자 콘솔 (정산 승인, 신고 처리)
│  └─ api/              # NestJS, src/modules/{auth,script,talent,license,project,settlement}
├─ services/ai-worker/  # Python
├─ packages/
│  ├─ api-contract/     # OpenAPI 스펙 + 자동 생성된 클라이언트·타입
│  └─ ui/               # 공통 컴포넌트
├─ docker-compose.yml
└─ .github/{workflows/, CODEOWNERS}
```

### 핵심 규칙

1. **로컬 환경은 명령 하나로 실행한다.** `docker compose up` 한 번으로 Postgres, Redis, MinIO, AI mock이 모두 떠야 한다. `.env.example`만 커밋하고, 실제 키는 Doppler나 1Password 같은 비밀값 관리 도구로 공유한다.
2. **API 명세를 먼저 정한다.** OpenAPI 스펙을 먼저 PR로 합의하고 클라이언트 코드를 자동 생성한다. 프론트는 백엔드가 완성되기 전에도 MSW mock으로 개발할 수 있다.
3. **AI 기능은 인터페이스와 mock으로 분리한다.** `SummaryProvider`, `VoiceSynthProvider` 같은 인터페이스를 두고, 로컬에서는 가짜 결과를 바로 돌려준다. GPU가 없는 노트북으로도 전체 흐름을 개발할 수 있다.
4. **브랜치 전략은 GitHub Flow.** `main`은 보호 브랜치로 두고, 기능 브랜치는 1~3일 안에 머지한다. PR마다 1명 이상 리뷰하고 squash merge한다. `CODEOWNERS`로 모듈별 리뷰어를 자동 지정한다.
5. **CI는 GitHub Actions.** PR마다 lint, 타입 검사, 테스트, 마이그레이션 검증을 실행하고, 프론트는 PR별 미리보기 배포를 띄운다. `main`에 머지되면 dev 환경에 자동 배포한다.
6. **DB 마이그레이션은 도구로만 만들고, 이미 머지된 마이그레이션은 수정하지 않는다.**

배포 환경: `local → dev → staging (PG 테스트 모드) → prod`

> **주의:** dev와 staging에는 실제 배우의 얼굴이나 목소리를 넣지 않는다. 테스트 데이터는 AI로 만든 가상 인물이나, 동의한 팀원 본인 데이터로만 채운다.

## 4. 처음부터 설계에 넣어야 할 것

이 플랫폼의 핵심 가치는 "합법적으로 쓸 수 있다"는 점이다. 아래 항목은 나중에 붙이기 어려우니 처음부터 데이터 모델에 넣는다.

### ① 동의·라이선스 기록 (가장 중요)

- 얼굴·음성 자산마다 저장할 정보: 허용 용도, 금지 카테고리(성적·정치·혐오 콘텐츠), 사용 기간, 변형 허용 범위, 단가
- 유효한 `license_id`가 없으면 AI 워커가 합성을 거부한다. API에서 한 번 확인하고, 워커에서도 다시 확인한다.
- 동의를 철회하면 새 합성을 즉시 막는다. 기록은 추가만 가능한(append-only) 감사 로그로 남긴다.
- 대본 AI 요약에서 장르와 수위를 분류해, 배우가 허용한 범위와 자동으로 대조한다.

### ② 본인 확인

- 휴대폰 본인인증과 얼굴 라이브니스 검사(실제 본인이 촬영 중인지 확인)를 함께 한다. 남의 얼굴을 자기 것처럼 등록하는 것이 가장 큰 악용 경로다.
- 만 14세 미만은 개인정보 수집에 법정대리인 동의가 필요하다.
- 만 19세 미만은 라이선스 계약에 법정대리인 동의가 필요하다(민법).

### ③ 데이터 보호

- 얼굴·음성 원본과 특징값(임베딩)은 민감정보인 생체인식정보로 볼 여지가 있다.
  - 일반 동의와 별도로 동의를 받는다.
  - 분리된 저장소에 암호화해서 보관한다(KMS).
  - 접근 로그를 남긴다.
- 해외 AI API로 얼굴이나 음성을 보내면 개인정보 국외 이전 고지·동의가 필요하다.

### ④ 생성물 표시

- 2026년 1월 시행된 AI 기본법에 따라 AI 생성물임을 표시한다. 영상에 워터마크와 C2PA 메타데이터를 넣는다.
- 생성 이력(누가, 어떤 라이선스로, 언제)을 DB에 남긴다.
- 딥페이크 악용에 대비한 신고·삭제 절차와 관리자 도구를 만든다.

### ⑤ 정산

- 플랫폼이 대금을 직접 보관했다가 나눠주면 전자금융업 등록 문제가 생길 수 있다. PG사(토스페이먼츠, 포트원 등)의 지급대행·분할정산 상품을 쓴다.
- 장부는 복식부기 방식으로 만든다.
  - 금액은 원 단위 정수로 저장한다(소수점 자료형 금지).
  - 잘못된 기록은 지우지 않고 반대 거래를 추가해 바로잡는다(역분개).
- 결제와 웹훅 처리에는 idempotency key를 넣어 중복 지급을 막는다.
- 세금 처리
  - 개인 프리랜서: 3.3%(사업소득) 또는 8.8%(기타소득) 원천징수, 지급명세서 제출
  - 사업자: 세금계산서 발행
- 생성 이력이 곧 초상·음성 사용료의 정산 근거가 되도록 ①과 연결한다.

> 신인 배우는 "널리 알려진 사람"이 아니라서 부정경쟁방지법의 퍼블리시티권 보호를 받기 어려울 수 있다. 결국 플랫폼의 라이선스 약관이 배우를 보호하는 핵심 장치다. 약관과 동의서는 변호사 검토를 받는다.

## 5. 역할 분담 (2명)

프론트/백엔드로 나누면 한쪽이 다른 쪽을 기다리는 시간이 생긴다. 2명이면 **기능 단위로 나눠 각자 화면과 API를 끝까지** 만드는 편이 빠르다.

| 담당 | 범위 |
|---|---|
| A | 회원가입·로그인, 제작자 쪽 흐름 (대본 목록·검색, 제안 보내기) |
| B | 작가 쪽 흐름 (대본 등록·수정·공개, 받은 제안 확인, 수락·거절 → 매칭) |

DB 스키마(`schema.prisma`) 변경은 충돌이 잦으니 항상 상대방 리뷰를 받는다. 인원이 늘면 1장의 모듈 단위로 담당을 나눈다.

## 6. 개발 순서

1. **개발 환경** (완료): 모노레포, Docker Compose, DB 스키마 초안
2. **MVP — 중개**: 회원가입·로그인, 대본 등록·공개, 대본 목록·검색, 제작 제안, 수락 → 매칭, 매칭 후 연락 수단
3. **AI 요약**: LLM API로 대본 요약과 장르·수위 분류. 제작자가 대본을 고르기 쉬워진다.
4. **계약·정산**: PG 연동, 작가·제작자 간 결제와 지급
5. **배우·성우**: 자산 등록, 본인 확인, 라이선스, 음성 합성
6. **얼굴 합성**: 법적·기술적 위험이 가장 커서 마지막에 한다.
